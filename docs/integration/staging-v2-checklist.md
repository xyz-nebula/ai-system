# Стыковка с серверным AI v2

Проверено 27 сентября 2026. Это интеграционный стенд, не приёмка качества судейства.

## Адрес и доступ

- AI v2: `http://172.16.34.7:8002`, приватная сеть.
- Старый AI v1 на `http://172.16.34.7:8000` оставлен без изменений.
- `GET /health/live`, `GET /health/ready`, `GET /openapi.json` доступны без токена.
- Модельные операции требуют `Authorization: Bearer <ARENA_SERVICE_TOKEN>`
  и `X-Arena-Contract-Version: 2.0.0-rc.1`.
- Используется существующий защищённый серверный токен. Передать его владельцу
  Backend через хранилище секретов, не через этот документ или браузер.

Маршруты `/v2/turn`, `/v2/finish`, `/v2/preparation/review`, `/v2/evaluate`
опубликованы в серверном OpenAPI. `evaluate` оценивает уже готовый диалог;
он не генерирует игровые ответы и не заменяет управляемый ход.

## Первый интеграционный срез: оценка сохранённого диалога

Backend вызывает `POST /v2/evaluate`. Формат и модели:
[полный контракт](simple-evaluation-request.md).

Соответствие актуальному Backend `dev` на коммите
`4af14edb38f0126695105f9004634e311d81b338`:

| Поле запроса AI | Источник Backend |
| --- | --- |
| `role` | `Case.first_role`, если `Chat.selected_role=0`; иначе `Case.second_role` |
| `opponent_role` | Другая из двух ролей Case |
| `case_description` | Общая фабула `Case.description`; проверить полноту и отсутствие скрытых вводных |
| `messages` | Сохранённые сообщения Chat по возрастанию `Message.sequence`, объекты только `{text, is_ai}` |
| `preparations` | `Chat.preparations`; пустую/пробельную строку преобразовать в `null` |

`Case.first_role_preparations` и `second_role_preparations` не подставляются вместо
личной подготовки Chat. `system_prompt` и скрытые вводные оппонента не отправляются
в описание для оценки. Не склеивать автоматически все поля Case: полноту общей
фабулы подтверждает владелец кейсов.

В проверенном `ChatService` пока нет HTTP-вызова AI: `post_message` сохраняет текст,
а методы создания Feedback/Judgement сохраняют переданный текст. Это не вызов оценки.

### Что сделать Backend

1. Настроить серверный AI client с адресом 8002, внутренним токеном и заголовком версии.
2. В завершении Chat зафиксировать неизменяемый транскрипт и вызвать evaluate один раз.
   Авторство брать из доверенного сохранённого потока, не произвольного флага браузера.
3. Проверять ответ по `EvaluationResponse`, сохранять весь структурированный результат
   вместе с привязкой к Chat. Текущие текстовые Feedback/Judgement сами по себе
   не обеспечивают контракт выдачи структурированной оценки Frontend.
4. Передать Frontend исход, три независимых судейских слота и Trainer с их статусами.
   Не сводить `failed` к `defeat`, нулю или отсутствию соглашения.
5. Учитывать потенциальные 300 секунд обработки; согласовать ожидание/фоновую задачу
   на стороне Backend. AI API сейчас синхронный, отдельного job/poll API у него нет.
   Не делать слепой retry после неоднозначного таймаута.

### Что сделать Frontend

Показать ожидание оценки, затем каждый слот отдельно. `failed` означает «оценка
недоступна», а не проигрыш. Не показывать методические источники. AI-токен остаётся
только в Backend. Название внешнего маршрута получения результата определяет Backend.

### Audio и полный диалог

Audio → Backend → AI; прямого стыка Audio → ai-system не требуется.
Для полноценного поединка отдельно проверить управляемые ходы и сохранение снимка
по [общему интеграционному руководству](unified-integration-guide.md).
Рабочая оценка сохранённого диалога ещё не доказывает интеграцию оппонента/Guard/STT/TTS.

## Уже проверено и что не проверено

На сервере: health/readiness HTTP 200; маршруты в OpenAPI; без токена HTTP 401,
неверная версия HTTP 409, пустое тело с корректными заголовками HTTP 422.
Существующий v1 health возвращает HTTP 200. LocalAI и RAG не перенастраивались.

Один синтетический запрос через публичный `/v2/evaluate` с настоящими LocalAI,
Qdrant и embeddings: HTTP 200 за 68.63 с; ответ прошёл `EvaluationResponse`.
Исход `agreement` ready, Trainer ready, negotiation ready; hiring и ownership
failed с `invalid_judge_output`. Это частично успешная оценка, не зелёная приёмка
всех судей и не тест Backend/Frontend. Автоматического повтора не было.

На этой серверной среде Backend, Frontend и Audio контейнеры не обнаружены.
В GitHub Backend deployments записей нет; это не доказывает отсутствие сервисов
на других машинах. Для настоящего командного e2e нужны адрес развёрнутого Backend,
его версия и реализация вызова AI. В чужих репозиториях изменений не сделано.

Версия стенда: image `arena-ai:integration-v2-20260927-01`, контейнер
`arena-ai-v2-integration`. Собран из текущего рабочего дерева поверх `f766289`,
не из отдельного опубликованного коммита. Не считать GitHub HEAD точным снимком стенда.
Остановить только этот стенд при необходимости: `docker stop arena-ai-v2-integration`.
Существующие AI v1, LocalAI и RAG при этом не трогать.

### Воспроизводимый запуск этого отдельного стенда

После сборки указанного image, из серверного SSH-сеанса:

```bash
docker run -d --name arena-ai-v2-integration --network host \
  --env-file /home/farrahovd234/arena-ai/shared/.env \
  -e ARENA_V2_ENABLED=true --user 10001:10001 --read-only \
  --tmpfs /tmp:size=16m,mode=1777 --cap-drop ALL \
  --security-opt no-new-privileges --pids-limit 128 --memory 1g --cpus 2 \
  --restart unless-stopped --log-opt max-size=10m --log-opt max-file=3 \
  arena-ai:integration-v2-20260927-01 \
  uvicorn arena_ai.app:app --host 172.16.34.7 --port 8002 \
  --no-access-log --log-level warning
```

Не повторять создание существующего контейнера и не удалять его автоматически.
Перед новым запуском проверить отсутствие чужого listener на 8002.
Этот стенд запускается отдельно от production-compose на 8000; замена основного
релиза после приёмки выполняется по серверному руководству с возможностью отката.
