# Упрощённый запрос оценки диалога

Формат запроса согласован. Предлагаемый маршрут: `POST /v2/evaluate`.
**Маршрут пока не реализован и не развёрнут.** Существующий `/v2/finish` не изменён.
Этот запрос предназначен для оценки готового диалога, не для ответа AI-оппонента.

## Pydantic-модель для Backend

Готовый самостоятельный файл: [evaluation_request.py](../../src/arena_ai/v2/evaluation_request.py).
Можно скопировать его в Backend: зависимость только от Pydantic 2, без импортов AI-проекта.
Основная модель — `EvaluationRequest`, сообщение — `EvaluationMessage`.

```json
{
  "role": "Менеджер",
  "opponent_role": "Директор",
  "case_description": "Менеджер и директор обсуждают условия повышения.",
  "messages": [
    {"text": "Какие условия повышения вы предлагаете?", "is_ai": false},
    {"text": "Давайте обсудим результаты и ответственность.", "is_ai": true}
  ],
  "preparations": "Моя цель — выяснить условия повышения. План — спросить об условиях."
}
```

## Правила передачи

- `role` и `opponent_role` — выбранные активные игровые роли пользователя и AI.
- `case_description` — общая фабула и условия. Не передавать скрытые вводные оппонента.
- `messages` — непустой список сохранённых реплик в хронологическом порядке.
  У каждого объекта ровно два поля: `text` и `is_ai`.
  Backend определяет авторство по сохранённым данным, а не доверяет флагу с Frontend.
  Не включать технические промпты, ошибки модели и отклонённые попытки как реплики диалога.
- `preparations` — собственная подготовка пользователя одной строкой.
  Можно не передавать или передать `null`. Пустую/пробельную подготовку Backend преобразует
  в `null`. Это не две авторские подготовки игровых ролей из Case.
- Текстовые значения должны содержать непробельный символ. Исходные пробелы и переносы
  сохраняются для точного цитирования. `is_ai` принимает только JSON `true`/`false`,
  не строки и не числа. Неизвестные поля запрещены.
- Не требуется строгое чередование авторов: система не должна выдумывать пропущенные реплики.

По такому запросу исход переговоров можно оценить по тексту, но это не подтверждение
сохранённой Backend сделки. Здесь нет достоверных временных меток или состояния сделки;
AI не должен их выдумывать. Договор об ответе и подключение HTTP-маршрута — следующий шаг.

Тренерский разбор после диалога использует `preparations` для сопоставления плана с действиями.
Проверка блока подготовки до диалога остаётся отдельной операцией `/v2/preparation/review`.
