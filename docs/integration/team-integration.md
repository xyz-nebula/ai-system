# Подключение AI-контура: гайд для команд

Этот гайд описывает действующий v1. Универсальный контракт v2 пока только
[предложен для согласования](contract-v2-handoff.md); новые поля в v1 не отправлять.

## Цель и текущий статус

Связать приложение в один проверяемый путь:

```text
Текст: Frontend → Backend → AI-сервис → Backend → Frontend
Голос: Frontend → Audio Engine (STT) → Backend → AI-сервис
       → Backend → Audio Engine (TTS проверенного ответа) → Frontend
Итоги: Frontend → Backend → AI /finish → Backend → Frontend
```

AI-сервис уже работает в отдельном серверном контейнере. Минимальный живой turn/finish
проверен с реальными Qwen, Qdrant и embeddings: три судьи и Trainer вернули ready.
Это не готовая сквозная интеграция приложения и не полная приёмка качества.
Известен отказ конструктивного хода `opponent_unearned_concession` в полном
adversarial-сценарии; его нельзя скрывать под demo-ответом или отключением проверок.

На проверенных dev-ветках Backend пока сохраняет чатовые сообщения без вызова AI,
Frontend не реализует `sendTextTurn` и возвращает demo-разбор,
Audio Engine напрямую мостит LocalAI realtime. Ниже — требуемые изменения, не
описание уже существующих возможностей этих компонентов.

## 1. Подключение и источник истины

| Параметр | Значение |
| --- | --- |
| AI base URL | `http://172.16.34.7:8000` |
| Авторизация turn/finish | `Authorization: Bearer <AI service token>` |
| Схема работающего сервиса | `GET /openapi.json` |
| Версия схемы в репозитории | [docs/api/openapi.json](../api/openapi.json) |
| Проверка процесса | `GET /health/live` |
| Проверка модельного gateway | `GET /health/ready` |

Адрес приватный. Проверять доступ **из среды/контейнера Backend**, а не только с
компьютера разработчика. В bridge-контейнере `localhost` означает сам контейнер,
не AI-сервер. Не открывать AI, Qdrant или embeddings в публичный интернет ради стыковки.
Для браузерного микрофона Frontend должен быть доступен по HTTPS, аудио — по WSS.

AI service token уже создан у оператора AI-деплоя; передать его Backend через
защищённое хранилище секретов. Не публиковать токен в Git, чат, query string или JS.
Это **не пользовательский JWT**. Браузер использует пользовательскую авторизацию
Backend; Backend отдельно авторизуется в AI.

Пример проверки сети из Backend-среды:

```bash
curl --connect-timeout 3 --max-time 10 http://172.16.34.7:8000/health/live
curl --connect-timeout 3 --max-time 10 http://172.16.34.7:8000/health/ready
```

Ожидаются HTTP 200 и `status=alive` / `status=ready`. Readiness модели не доказывает
готовность retrieval: для неё нужен также живой finish с готовыми судейскими слотами.
SSH-доступ, запуск и откат контейнера: [серверный гайд](server-deployment.md).

## 2. Backend: первый обязательный стык

### Конфигурация и данные

1. Добавить серверный HTTP client для AI. Предлагаемые имена настроек:
   `AI_SERVICE_URL` и `AI_SERVICE_TOKEN`; это новые настройки Backend, их обработку
   нужно реализовать, простое добавление в `.env` само по себе ничего не подключит.
2. Backend хранит канонические `CaseConfig` и `SessionSnapshot`, итог finish,
   начало/срок/окончание раунда и идентификаторы запросов. AI stateless: не загружает
   кейс по ID, не хранит сессии и не дедуплицирует вызовы.
3. Согласовать стабильный `case_id` и ролевое сочетание с Frontend. Название чата
   не заменяет ID и полную конфигурацию кейса. Закрытые вводные берутся из серверного
   каталога, а не из JSON, который прислал браузер.
4. Передавать утверждённые `agreement_rules` и `opponent_strategy`, когда они заданы
   кейсом. Не заменять лестницу уступок тестовыми значениями ради успешного ответа.

### Управляемый ход

AI endpoint: **`POST /v1/turn`**. Тело состоит из:

| Поле | Кто формирует |
| --- | --- |
| `case` | Backend: полный `CaseConfig`, включая закрытые вводные |
| `snapshot` | Backend: последний канонический снимок |
| `turn_id` | Backend: идентификатор конкретной попытки |
| `user_text` | Текст пользователя или финальный STT-транскрипт |

Начальный снимок:

```json
{
  "session_id": "<session-id>",
  "state": {"turn_count": 0},
  "transcript": []
}
```

Далее использовать **весь снимок, возвращённый AI**, не пересобирать его из сообщений
и не отбрасывать новые поля. Примеры полного запроса/ответа:
[managed-turn.json](../api/examples/managed-turn.json) и
[Backend-only позиция](../api/examples/backend-position-turn.json).
Redacted значения и вымышленные ID в примерах не являются рабочими вводными кейса.

Алгоритм Backend:

1. Проверить пользователя, владение сессией и состояние внешнего раунда.
2. Допустить не более одного активного AI-хода на сессию; исключить гонку с finish.
3. Зафиксировать идентификатор команды/попытки, передать канонический case/snapshot в AI.
4. Проверить HTTP-ответ и поле `status`; **HTTP 200 не означает accepted**.
5. Атомарно сохранить результат согласно таблице и отдать только публичную проекцию.

| AI status | Что сохранять | Что показать/озвучить |
| --- | --- | --- |
| `accepted` | Возвращённый snapshot | Проверенный `opponent_text` |
| `blocked` | Возвращённый snapshot с заблокированной попыткой | Безопасный `opponent_text`, не обычный успешный переговорный ход |
| `model_error` | Снимок не продвигать | Техническое сообщение, не игровой ответ; сохранить диагностический код отдельно |

После неоднозначного сетевого timeout **не повторять AI-вызов автоматически**.
AI может уже обработать запрос, а повтор запустит модель заново. Backend отвечает за
свои command records, дедупликацию и восстановление статуса, не AI.
Если результат неизвестен, не выдумывать реплику и не создавать второй ход.
При явном `model_error` повтор по действию пользователя возможен как новая попытка.

### Завершение и результат

AI endpoint: **`POST /v1/finish`** с `case`, последним каноническим `snapshot` и
необязательным `preparation`. Перед finish определить судьбу активного хода и последней
голосовой реплики: дождаться её фиксации либо явно сообщить, что она не вошла в поединок.
Не отправлять finish со старым снимком одновременно с его обновлением.

AI возвращает `session_id`, `outcome`, `judge_verdicts`, `trainer_feedback`.
Backend сохраняет этот результат и предоставляет его для повторного открытия страницы.
Не пересчитывать оценку модели и не заменять failed-слоты демонстрационными.
Пример: [preparation-finish.json](../api/examples/preparation-finish.json).

Договорённость — текущий исход, **не окончание раунда**. После `stage=agreed` можно
продолжать turn до внешнего завершения. Backend — источник времени раунда; Frontend
показывает его таймер. AI не запускает пятиминутный таймер. HTTP timeout — другое ограничение.
Finish без единого принятого хода возвращает HTTP 409.

Модельные операции могут быть значительно дольше стандартного frontend timeout 20 секунд.
Согласовать ожидание/асинхронный статус Backend и чтение сохранённого результата;
не компенсировать короткий timeout повторными вызовами модели.

### Публичная проекция

Браузеру нельзя отдавать сырой AI request/snapshot. Исключить закрытые вводные,
`opponent_private_phrases`, `opponent_strategy`, `opponent_progress` и внутренние
доказательства переходов. `opponent_progress` при этом обязательно хранить на Backend
и целиком передавать в следующий AI-запрос. Обычные цитаты принятого диалога допустимы.
Не логировать полные запросы, снимки, карточки подготовки и service token.

Внешние HTTP endpoints Backend для text-turn, finish и result согласовывает с Frontend
его команда: пути AI `/v1/turn` и `/v1/finish` — **межсервисные**, не готовые маршруты
текущего chat CRUD и не предложение направить браузер прямо в AI.

## 3. Frontend: реальный текстовый путь и аналитика

1. Заменить `sendTextTurn` из `feature-unavailable` на согласованный Backend endpoint.
   Показывать ожидание и подтверждённые Backend сообщения; не добавлять выдуманный AI ответ.
2. Заменить demo в `finishSession`/`getResult` настоящим сохранённым результатом Backend.
   Обработать processing, транспортный сбой и частично готовый результат без слепого retry.
3. Передавать выбранные `case_id`/роли и заполненные поля подготовки по контракту Backend.
   Пустая карточка допустима. Она поступает только в finish и нужна Trainer, не судьям.
4. Не закрывать экран переговоров автоматически после соглашения. Таймер/явный finish
   следуют состоянию Backend, а не тексту оппонента.
5. После reload читать историю и итог с Backend; дедуплицировать подтверждённые сообщения.

### Отображение аналитики

| AI поле | Публичный смысл |
| --- | --- |
| `outcome.kind` | `agreement`, `partial_agreement`, `deferred`, `no_agreement`: факт исхода, не оценка навыка |
| `judge_verdicts[].college` | `hiring` — нанимающиеся; `negotiation` — отправляющие на переговоры; `ownership` — доверяющие собственность |
| `verdict.choice` | `player` или `opponent`: выбор этой коллегии, не общий score |
| `decisive_criterion` | Один решающий критерий |
| `evidence_turn_id`, `evidence_quote` | Подтверждённый эпизод диалога |
| `observation`, `effect`, `comparison` | Что произошло, что изменилось, чем отличались участники |
| `trainer_feedback.feedback` | Отдельный тренерский разбор: summary, strengths, mistakes, next_try |
| `feedback.plan_vs_reality` | Необязательное сопоставление подготовки: followed, adapted, not_observed |

Не сводить эту схему к старому demo `victory/defeat`, `score=74` и общему summary.
Если нужен общий балл, это отдельное продуктовое решение; текущий AI-контракт его не выдаёт.
Судья объясняет голос, Trainer даёт советы — не смешивать их в один комментарий.
Не показывать названия методик, источники, ссылки, страницы, выдержки или блок provenance.

Каждый judge slot и Trainer имеет `status=ready|failed`. При failed показать
«Разбор временно недоступен» для конкретного слота, сохранив остальные ready.
Это не проигрыш пользователя и не повод подставлять demo. `verdict`/`feedback` при failed
равен null. Не отправлять service token в браузер даже ради временной проверки.

## 4. Audio Engine: не обходить управляемый ход

1. Сохранить ответственность за микрофонный поток, VAD/STT и TTS.
2. Финальный STT-текст отправлять в согласованный Backend endpoint управляемого хода.
   Backend проверяет пользователя/сессию и вызывает AI точно так же, как для текста.
3. Озвучивать только `opponent_text`, подтверждённый Backend после AI-проверки.
   Для blocked это безопасная реакция. Для model_error не запускать альтернативную
   генерацию игрового ответа и не продвигать историю; допускается техническое сообщение.
4. Подтверждённые реплики сохраняет Backend. Не писать тот же voice turn повторно через
   старый message endpoint после того, как управляемый ход уже сохранён.
5. Согласовать порядок кадров/финальных реплик, паузу, reconnect, владение сессией
   и последнюю реплику перед finish. Публичный пользователь не должен иметь возможность
   записать произвольное сообщение как будто его сказал проверенный AI.

Текущий direct LocalAI realtime response нельзя просто переслать пользователю, а потом
проверить постфактум: звук уже раскроет непроверенный ответ и обойдёт Guard/Validator.
Нужно разделить распознавание речи и озвучивание проверенного текста. Если текущая
модель/интерфейс этого не поддерживает, явно согласовать другой STT/TTS путь.
Конкретный WebSocket/STT/TTS контракт — зона Audio Engine, не endpoint AI-сервиса.

## 5. Ошибки: обязательная обработка

| Ответ/код | Реакция интеграции |
| --- | --- |
| HTTP 401 от AI | Проверить серверный service token; не refresh пользовательского JWT |
| HTTP 422 | Исправить тело по OpenAPI; не повторять неизменённый запрос |
| HTTP 409 на finish | Нет принятого хода; показать понятное состояние, не выдумывать итог |
| HTTP 503 readiness | Gateway/модель не готовы; диагностировать связь/конфигурацию |
| `model_error` в HTTP 200 | Ход не принят, snapshot не продвинут |
| Неоднозначный timeout | Не повторять AI-вызов автоматически, не создавать второй ход |
| `judge_retrieval_unavailable` | Qdrant/embeddings недоступны; передать диагностику AI/Infra, сохранить другие слоты |
| `invalid_judge_retrieval` | Корпус/индекс не прошёл проверку; нет fallback |
| `judge_unavailable`, `invalid_judge_output` | Нет вердикта этой коллегии, другие слоты остаются действительными |
| `trainer_unavailable`, `invalid_trainer_output` | Нет Trainer-разбора, судейские слоты сохраняются |

## 6. Порядок подключения и критерии приёмки

1. **Backend + AI:** из Backend-контейнера доступны health endpoints; реальный turn
   сохраняет возвращённый снимок; следующий ход использует его; finish сохраняет итог.
2. **Frontend + Backend, текст:** пользователь входит, выбирает кейс, отправляет реплику,
   получает настоящий ответ, завершает раунд, видит реальных судей/Trainer; после reload
   история и результат совпадают с сохранёнными. Нет demo-подмены и утечки private fields.
3. **Audio + Backend:** одна финальная STT-реплика создаёт один управляемый ход;
   TTS озвучивает проверенный ответ. Повторное соединение не создаёт дубли.
4. **Полный голосовой путь:** HTTPS/WSS, микрофон → STT → AI turn → TTS; финальная
   реплика учтена перед finish, результат доступен после обновления страницы.
5. **Негативные сценарии:** blocked, model_error, потеря сети, partial failed finish,
   продолжение после соглашения, внешний timer/finish без гонки с текущим ходом.
6. **Качество и нагрузка:** отдельно пройти полный adversarial acceptance, экспертную
   проверку вердиктов и тест шести одновременных пользователей. Минимальный smoke
   или mock/process тест не доказывает эти пункты.

## 7. Что передать AI-команде для совместной проверки

- Адреса живых Backend, Frontend и Audio Engine, версии/commit SHA и доступ из приватной сети.
- Согласованные внешние endpoints text-turn, finish/result и voice commit.
- Стабильные case ID/роли и источник канонической конфигурации.
- Способ проверки Backend → AI из его контейнера и безопасного подключения service token.
- Результат text e2e и voice e2e: статусы, request/session IDs и коды ошибок,
  без токенов, сырых снимков, методического payload и закрытых вводных.

До выполнения этих пунктов не объявлять приложение полностью интегрированным.
Менять чужие репозитории и контейнеры должны их владельцы; данный гайд описывает
стык и критерии проверки, не предоставляет разрешение на их изменение.
