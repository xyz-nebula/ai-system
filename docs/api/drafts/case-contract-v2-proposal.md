# Проект AI-контракта v2: кейс, поединок и подготовка

**Исторический неполный draft.** Цель новой реализации теперь описана в
[единой спецификации 2.0.0-rc.1](../v2/README.md). Схемы и поля этих двух
версий не смешивать; работающий runtime пока остаётся v1.

**Статус: проект для согласования, не работающий API.** Дата: 2026-09-26.
`/v2/turn` и `/v2/finish` пока не реализованы и не развёрнуты. Текущий
[OpenAPI v1](../openapi.json) не изменён; новые поля нельзя отправлять в v1.
Названия v2 фиксируются только после ответа команд и сверки с владельцем бизнес-модели.

Повторный [аудит FR v0.3 и других репозиториев](../../integration/project-requirements-and-fields-audit.md)
выявил не покрытые этим draft требования: проверку блока подготовки, время
транскрипта, цену/последствия исхода, полную конфигурацию пар и универсальных границ.
Перед утверждением схема требует дополнений; её валидация не доказывает полноту FR.

## Источники и пределы проекта

- [Структура кейса](https://github.com/xyz-nebula/knowledge-base/blob/master/business/Структура%20кейса.md).
- [Подготовка к роли](https://github.com/xyz-nebula/knowledge-base/blob/master/business/Подготовка%20к%20роли.md).

- [Распределение работы и сообщение команде](../../integration/contract-v2-handoff.md).

Пользователь подтвердил поединок 1×1: пользователь и AI, с учётом остальных
участников ситуации. Это ограничение активного диалога, не требование к числу участников
полного кейса. Многосторонний разговор с несколькими активными AI требует отдельного решения.
Ни этот проект, ни примеры не утверждают авторские значения реальных кейсов.

## 1. Кто чем владеет

| Объект | Владелец | Правило |
| --- | --- | --- |
| Полный бизнес-кейс | Backend/админка, содержание утверждает автор кейса | Название, короткое/полное описание, категория, сложность, длительность, все участники, интересы, вводные ролей |
| AI-проекция `CaseConfig` | Backend формирует, AI валидирует | Только нужные вводные выбранных ролей и разрешённый контекст остальных участников |
| Карточка подготовки | Пользователь; Backend хранит | Не подставлять интересы автора или цель кейса вместо собственных ответов пользователя |
| Канонический снимок | Backend | AI возвращает следующий снимок, не хранит сессии и не дедуплицирует вызовы |
| Команды, таймер и доступ | Backend | Пользовательский JWT, владение, очередь, deadline, finish, retry и сохранение результатов |
| Модельные решения | AI | Оппонент, Guard/Validator, проверка уступок, судьи, Trainer |
| Аудио | Audio Engine | STT и TTS только проверенного ответа; не обходить управляемый ход |

Категория, короткое описание и `duration_seconds` остаются на Backend. Difficulty
пока является метаданными: бизнес-правило изменения поведения от сложности не задано.
Если оно появится, автор должен утвердить явные параметры поведения, а не угадываемые AI значения.

## 2. Формат и проверяемая схема

[JSON Schema draft 2020-12](case-contract-v2.schema.json) содержит `$defs` всех
межсервисных объектов. Корень проверяет TurnRequest или FinishRequest; для ответа
выбирать `$defs/TurnResponse` либо `$defs/FinishResponse`. Все объекты запрещают
неизвестные поля. Схема проверяет форму; межполевые правила ниже обязательны отдельно.
Это проект JSON Schema, **не экспорт OpenAPI из реализованного приложения**.

Строковые ID непрозрачны: UUID допустим как строка. Обязательное поле может
допускать `null`, только если это явно указано. Пустой список не равен отсутствующему полю.
Подготовка передаётся одной непустой строкой либо отсутствует/null.

### `CaseConfig`

Все поля таблицы обязательны; для отсутствующей стратегии используется `null`.

| Поле | Тип | Что передаёт Backend |
| --- | --- | --- |
| `id` | string | Стабильный ID бизнес-кейса |
| `config_version` | string | Неизменяемая версия вводных/правил; изменение содержимого создаёт новую версию |
| `title` | string | Название кейса |
| `shared_context` | string | Полная значимая фабула, которую разрешено знать обеим выбранным ролям |
| `participants` | Participant[] | Все значимые участники ситуации, включая неактивных, например HR |
| `player` | RoleBrief | Вводные выбранной роли пользователя |
| `opponent` | RoleBrief | Вводные выбранной роли AI |
| `negotiables` | Negotiable[] | Каталог допустимых предметов торга и их типов/единиц |
| `opponent_strategy` | OpponentStrategy или null | Авторская лестница позиции и основания уступок |
| `opponent_private_phrases` | string[] | При наличии — явно закрытые формулировки; отсутствие списка не отменяет защиты закрытых вводных |

`Participant`: `id`, `name`, `public_context`, `public_interests: string[]`.
В эти поля попадает **только публичная** информация. Приватные интересы не делать
публичными автоматически из-за того, что они перечислены в авторском документе.

`RoleBrief`: `role_id`, `private_context`, `interests: Interest[]`, `batna: string|null`.
`Interest`: `text`, `visibility: public|private`. Это исходные интересы роли,
а не заполняемый пользователем SWOT или его переговорная цель. `batna` здесь —
авторская альтернатива роли, если она задана; её нет — `null`, не выдумывать.

ID участников уникальны. Player и opponent — разные ID из participants.
Публичные интересы RoleBrief должны быть согласованы с публичной проекцией.
Закрытые вводные остальных ролей Backend хранит отдельно и не передаёт AI без
авторского решения об их доступности выбранному оппоненту.
Автор должен явно определить, какие факты общие, а какие известны только отдельной роли.

### Универсальные предметы торга и обязательства

`Negotiable`:

| Поле | Значение |
| --- | --- |
| `id` | Стабильный ID параметра внутри версии кейса |
| `label` | Понятное название: цена, срок, объём, формат работы и т. п. |
| `value_type` | `number`, `text`, `boolean`, `choice` или `date` |
| `unit` | Явная единица либо null: day, percent, RUB/item; AI не угадывает единицы |
| `choices` | Разрешённые строки для choice; для остальных типов — пустой список |

`DealTerms`: `values: TermValue[]`, `commitments: Commitment[]`.
`TermValue`: `term_id`, `value` (JSON number/string/boolean, согласно типу параметра).
`Commitment`: `role_id`, `text`. Нет обязательных employee/director и salary/KPI полей.

Правила: уникальные term_id; неизвестные ID запрещены; boolean не является number;
date — строка `YYYY-MM-DD`; choice строго из choices. В terms каждой ступени
каждый объявленный предмет торга встречается ровно один раз. Обязательства относятся
к одной из двух активных ролей, не к неучаствующему HR. Пустые values допустимы
для кейса без параметров, но договорённость должна содержать хотя бы одно условие
или обязательство. Числа без привязки к единице не конвертировать автоматически.

Лестница сохраняет `steps`: ровно одна начальная declared, одна target, одна
конечная red_line; между ними могут быть intermediate. Step: `id`, `kind`, `terms`,
`requires`. Declared не требует уступок; остальные имеют хотя бы одно требование.
Требование: `id`, `description`, `direct_commitment_markers`, `evidence_groups`.
Маркеры — подсказка для проверки цитаты, не разрешение уступать по совпадению одного слова.

Переход только на следующую разрешённую ступень при новом подтверждённом встречном
действии; мат/повтор/угроза бизнесу сами по себе не основание. ID требований уникальны
во всей лестнице. Нельзя переносить v1-правило «все числа всегда уменьшаются»:
например, встречное увеличение объёма заказа может обосновывать снижение цены.
Автор задаёт допустимые пакеты условий явно; AI не конструирует произвольные
числовые условия вне лестницы. Дополнительное обязательство требует явного
доказательства, согласия соответствующей стороны и проверки непротиворечивости.

Если в negotiables есть параметры, opponent_strategy обязательна по межполевому
правилу. `null` допустим только для кейса без такой лестницы и без negotiables;
не считать это эквивалентом проверяемой числовой красной черты. Никакого fallback
на KPI/недели/повышение. Это ограничение первого v2, а не универсальный решатель любых сделок.

## 3. Подготовка пользователя

`preparation: string|null` передаётся только в finish и необязательна.
По уточнению команды Frontend склеивает заполненную подготовку, Backend хранит
одну строку и передаёт её Trainer без преобразования в структурированную карточку.
Роль определяется выбранной ролью сессии; Backend не смешивает подготовку разных ролей.
Пустой/пробельный текст Backend нормализует в null. Рекомендуются подписи разделов
и разделители; это рекомендация сериализации, а не дополнительные обязательные поля:

```json
{"preparation":"Цель: согласовать условия. Желаемая позиция: две недели. Красная черта: без бессрочной отсрочки. Вопросы: как проверяем результат?"}
```

Текст может включать анализ конфликта/слоёв, SWOT, цель, ЗП/ЖП/КЧ, BATNA, вопросы,
аргументы, варианты решения и фиксацию. Отсутствующие разделы не считаются ошибкой.
AI не требует заполнить всю методологию и не восстанавливает пропущенные ответы.
Это записи пользователя, не доказательство того, что он действительно так действовал.
ЗП/ЖП/КЧ пользователя не подменяют авторскую лестницу AI. Подготовленная первая реплика не
становится ходом автоматически: отправка в turn — отдельное явное действие.
Фиксация в плане не равна достигнутой договорённости в snapshot.
Не вводим обязательный эталон заполненной подготовки: бизнес-документ описывает
метод подготовки, необходимость авторских образцов согласуется отдельно.

## 4. Управляемый ход

Предлагаемый маршрут: `POST /v2/turn`. Авторизация между Backend и AI — тот же
принцип server-only service token; пользовательский JWT проверяет Backend.

`TurnRequest`: `case`, `snapshot`, `turn_id`, `user_text`. Подготовки здесь нет.
Backend назначает turn_id для попытки, передаёт текст или финальный STT.
Внешний client_request_id для дедупликации браузера хранит Backend отдельно.

`SessionSnapshot`:

| Поле | Источник |
| --- | --- |
| `schema_version` | Литерал `2.0` |
| `session_id` | ID поединка, назначенный Backend |
| `case_id`, `case_config_version` | Привязка к замороженной конфигурации кейса |
| `player_role_id`, `opponent_role_id` | Неизменяемое ролевое сочетание |
| `state` | turn_count, stage, agreement, decision, opponent_progress |
| `transcript` | Записи turn_id/speaker/status/text/blocked_reason |

Старт: turn_count=0, stage=negotiating, agreement/decision/opponent_progress=null,
transcript=[]. Case и snapshot должны совпадать по ID/версии/ролям. Несовпадение
отклоняется как invalid request, а не «исправляется» AI. Версия и роли не меняются
по ходу сессии; смена роли/кейса — новый поединок.

Состояния: negotiating — нет agreement и decision; agreed — есть agreement, нет
decision; partial_agreement/deferred — соответствующий decision, нет agreement.
Agreement использует универсальные DealTerms. PartialDecision: kind,
commitments (Commitment[]), open_points (string[]); DeferredDecision: kind, reason,
next_step. Это исход обсуждения, **не статус закрытия внешнего раунда**.

Progress хранит current_step_id, satisfied_requirement_ids и last_transition:
from_step_id/to_step_id/requirement_ids/evidence_turn_id/evidence_quote. Только
Backend/AI; браузеру/судьям/Trainer не передавать. Доказательство перехода — полный
текущий пользовательский текст, как в действующей проверке, не пересказ.

Ответ сохраняет знакомую форму: session_id, turn_id, status, opponent_text,
snapshot, error_code. ID должны соответствовать запросу.

| status | Что делает Backend |
| --- | --- |
| accepted | Атомарно сохраняет следующий снимок и результат команды; показывает/озвучивает проверенный ответ |
| blocked | Сохраняет следующий снимок с blocked/safe_reaction; это не обычный успешный переговорный ход |
| model_error | Не продвигает snapshot; показывает техническую ошибку, не озвучивает её как слова персонажа |

Accepted/blocked увеличивают turn_count на 1 и добавляют пару записей; model_error
возвращает исходный снимок. В паре player/opponent один turn_id. Иные попытки не
переписывают уже принятую историю. Новые неизвестные error_code показываются как
технический сбой без падения интерфейса; известные коды v1 сохраняют смысл.
HTTP 200 не означает accepted. Некорректная форма/межполевые связи — HTTP 422;
без service token — 401; finish без принятого хода — 409.

## 5. Завершение и аналитика

Предлагаемый маршрут: `POST /v2/finish`.
Тело: case, последний snapshot, необязательная preparation (можно отсутствующее/null).
Backend завершает внешний раунд и исключает гонку с turn; agreement сам не закрывает его.

`FinishResponse`: session_id, outcome, judge_verdicts, trainer_feedback.
Outcome.kind: agreement/partial_agreement/deferred/no_agreement; поля summary,
agreement (DealTerms|null), commitments (Commitment[]), open_points (string[]),
next_step/reason (string|null). Это фактический исход, не балл/победа.

`agreement` означает согласованные условия; `partial_agreement` — часть обязательств
согласована, есть открытые вопросы; `deferred` — явно отложенное решение с следующим
шагом; `no_agreement` — договорённость не зафиксирована. Это ответ на вопрос,
чем закончились переговоры. «Личная цель игрока достигнута» — другой вопрос:
без явного критерия успеха нельзя автоматически приравнивать любую сделку к успеху.
В этом проекте нет обязательного `goal_achieved`; Trainer может обоснованно сравнить
явно записанную цель из подготовки с диалогом, но не выдумывать критерий автора.

Три JudgeSlot сохраняют v1-форму и college hiring/negotiation/ownership, status
ready/failed, verdict/error_code. Ready — verdict есть, error_code=null; failed —
verdict=null, error_code есть. По одному слоту каждой коллегии, без подмены demo.
Вердикт: choice player/opponent, decisive_criterion, evidence_turn_id/evidence_quote,
observation/effect/comparison. ID и дословная непрерывная цитата из принятой реплики;
критерий только своей коллегии; видимый комментарий <=120 слов, без методик/ссылок
на источники, внутренних маркеров и тренерских советов. Судьи не получают подготовку
пользователя и приватные интересы. Только их публичная проекция и диалог.

TrainerSlot сохраняет status/feedback/error_code. Feedback: summary, strengths,
mistakes, next_try, plan_vs_reality. Каждый CoachingPoint содержит точную цитату,
turn_id, action, situation_change, consequence; хотя бы один наблюдаемый эпизод.
Разбор выбранного пользователя, без зашитого имени «Менеджер».

В plan_vs_reality каждый item содержит `preparation_text`: дословный непрерывный
фрагмент исходной строки подготовки, а не JSON Pointer или восстановленное поле.
Тренер выбирает значимые явно сформулированные намерения; нельзя гарантировать
сопоставление каждого UI-поля после склейки. Неоднозначный текст не превращать
в выдуманную цель. Followed/adapted требуют
цитату принятого хода пользователя; not_observed — оба evidence-поля null.
Отсутствующая/пустая подготовка — plan_vs_reality=null, без наказания за её отсутствие.
Статус followed/adapted не является доказательством правильности педагогического вывода;
кроме автоматических проверок нужна экспертная приёмка.

## 6. Передача и безопасность

AI вызывает модели только с нужной проекцией: оппонент не получает приватные
вводные пользователя или его карточку; Guard — публичный контекст; судьи — публичный
кейс/состояние/диалог; Trainer — публичное плюс пользовательская подготовка.
Публичные данные сторон доступны всем этим потребителям. Приватное не раскрывать
даже перефразированием; фильтр точных private_phrases не заменяет эту проверку.

Браузеру не выдавать полный CaseConfig/snapshot. Backend формирует отдельный
публичный ответ, удаляет opponent RoleBrief, стратегию, progress и внутренние
доказательства. Вводные своей роли можно показывать пользователю только по
утверждённой бизнес-проекции. Чужие приватные интересы и service token не публиковать.
В логи не писать полные вводные/снимки/подготовку/provider payload/Authorization.

## 7. Переход с v1 и проверка готовности

1. Подтвердить проект командами, включая ролевую пару, подготовку, приватность и
   каталог предметов торга. Затем AI реализует v2 и экспортирует реальный OpenAPI.
2. V1 пока сохраняется; существующие v1-сессии продолжают работать по v1.
   Новые v2-сессии явно выбирают новую версию. Не конвертировать снимки на лету.
3. Старые CaseConfig/PreparationCard не смешивать с v2. Перенос авторских кейсов
   и старой подготовки — явная миграция с сохранением оригинала и проверкой;
   ситуация в свободном тексте не имеет единственного безошибочного структурного mapping.
4. Backend проверяет настоящую схему `/openapi.json` из своей серверной среды.
   До появления v2 в схеме и согласованного релиза v2-URL не использовать.
5. Сквозная приёмка на согласованном кейсе про повышение и на другом кейсе без KPI:
   text → turn → snapshot → finish → 3 судьи + Trainer → UI; затем тот же путь с голосом.
6. Старые сессии и результаты сохраняются. Миграции БД и деплой в окно без активных
   поединков, с backup/rollback; отдельно нагрузка и экспертная оценка качества.
