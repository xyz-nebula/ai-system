# Что согласовать с Backend и Frontend

Изменения реализованы только в `ai-system`. Контракт — [OpenAPI](openapi.json), безопасные
примеры и условия завершения — [интеграционная инструкция](README.md).

## Backend

- Хранить канонические `CaseConfig` и `SessionSnapshot`; назначать `turn_id` и допускать один
  активный ход на поединок. После неоднозначного timeout не повторять ход автоматически.
- Передавать `case.opponent_strategy`, если в кейсе задана лестница уступок. Сохранять и возвращать
  в следующий AI-запрос `snapshot.state.opponent_progress` целиком, включая доказательство
  последнего перехода. Не вычислять прогресс самостоятельно и не отдавать его Frontend.
  [Backend-only пример](examples/backend-position-turn.json) использует вымышленные ID.
- `model_error` не продвигает снимок. `blocked` содержит безопасную реакцию и не является
  обычным принятым переговорным действием; сохранить именно возвращённый снимок.
- Договорённость — текущий результат, не окончание раунда. Разрешать следующие `/v1/turn`
  при `stage=agreed`. Только действие пользователя или истечение внешнего таймера вызывает
  `/v1/finish`; время начала/окончания раунда хранит Backend. HTTP timeout не заменяет таймер.
- В `/v1/finish` передавать итоговый снимок и заполненную часть карточки подготовки, если она
  есть. `judge_verdicts` и `trainer_feedback` — независимые слоты: failed-слот не отменяет ready.
  `judge_retrieval_unavailable` / `invalid_judge_retrieval` означают отсутствие вердикта,
  а не повод создавать замену на Backend или объявлять проигрыш пользователя.
- Методики в запрос не добавлять: индексирование, поиск и модельные роли принадлежат AI-контуру.

## Frontend

- Показать внешний таймер и явное завершение. Не блокировать поединок только из-за соглашения.
- Вердикт собирать из выбора, `decisive_criterion`, наблюдения, эффекта и сравнения. Точный
  `evidence_quote` связать с эпизодом `evidence_turn_id`, а не с внутренней методикой.
- Судейский вердикт объясняет голос, Trainer даёт советы; не смешивать их в один комментарий.
- Не показывать названия методик, ссылки, страницы, выдержки, Qdrant payload или внутренние ID
  ни под комментарием, ни в отдельном блоке источников. В публичном finish их нет.
- Не показывать закрытые вводные, `opponent_strategy`, `opponent_progress`, ступени позиции и
  доказательства внутренних переходов из Backend-only снимка.
- Для failed-слота показать «Вердикт временно недоступен»; сохранять готовые результаты других
  коллегий и тренера. Не подставлять универсальный комментарий или придуманную оценку.

## AI / Infra перед живой приёмкой

Запустить только Qdrant и embeddings, открыть SSH-туннель, выполнить smoke, загрузку корпуса
и `--check-index` по [инструкции retrieval](../judge-corpus.md). Порт LocalAI `8080` не трогать.
Модельный `/health/ready` не доказывает готовность retrieval. Локальные mock/process тесты
проверяют контракт, но не качество и доступность живых сервисов.

```bash
uv run arena-ai-eval --api-url http://127.0.0.1:8000 \
  --scenario adversarial --runs 1 --timeout 600 --progress \
  --output /tmp/arena-adversarial.json
```

Сценарий: мат → повторное оскорбление → угроза увести клиентов → ультиматум с выгодными
условиями без новых обязательств → конкретное встречное предложение → уточнение после
соглашения → явный finish. Положительное предложение, а не давление, должно обосновать уступку.
Выбор конкретного победителя не зафиксирован; проверяются самостоятельные критерии коллегий.
В отчёте 18 проверок; только их полное прохождение даёт exit `0`. Не принятый ход прекращает
прогон без retry, а не считается успешно обработанной агрессией. Проверки текста ограничены
известными маркерами и дословными совпадениями: экспертная оценка качества комментария всё ещё
нужна. Статусы в stderr (`--progress`) и JSON-отчёт не содержат реплик, приватного снимка,
методических payload, токенов или сырых ошибок провайдера.
