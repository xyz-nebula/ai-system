# HTTP v2: реализованный срез

Добавлен простой `POST /v2/evaluate` для сохранённых сообщений без CaseConfig/Snapshot.
Запрос `EvaluationRequest` не изменён; ответ содержит исход по тексту, три судейских
слота и Trainer с личной подготовкой. Цитаты ссылаются на нулевой индекс сообщения,
`is_ai` и дословный текст, без выдуманных ID/времени/состояния сделки.
Service token, версия заголовка и opt-in v2 обязательны. Схемы в рабочем OpenAPI.
Генерация и verifier делят 60 секунд на слот; вызовы последовательные.
Это дополнительный маршрут, не замена канонического `/v2/finish`.
Локальная приёмка не подтверждает деплой или качество на живой модели.
Полный формат и вызов: [гайд Backend](../../integration/simple-evaluation-request.md).
Узкий живой Trainer evaluate прошёл (20.00 с); полный evaluate не прошёл (56.77 с):
исход agreement проверен, hiring получил invalid_judge_output. Retrieval тестовый,
не серверный. Полное судейство/rollout остаются открытыми, гейты не ослаблялись.

Реализован `POST /v2/turn`. Добавлен первый фактический срез `POST /v2/finish`:
исход берётся из замороженного снимка. Пустой разговор получает согласованный
ответ без модели. У непустого добавлены генерация анализа уступок, цены и последствий
и отдельная независимая смысловая проверка. Общий таймаут обеих стадий — 60 секунд.
Модель получает только публичный контекст,
без личной подготовки и закрытых вводных. Цитаты проверяются по accepted message ID,
turn ID, автору, времени и дословному тексту; действия привязаны к активной роли.
При ошибке исход сохраняется, дополнительные массивы пусты, analysis_status=failed.
После проверки цитат второй вызов проверяет, подтверждают ли они именно сделанный
вывод. Только accept публикует анализ; reject/uncertain отбрасывают его целиком,
без ремонта и повторов до accept. Недоступность проверки также не публикует анализ.
Обе стадии используют одну модель, поэтому это дополнительный барьер, не гарантия
безошибочной интерпретации. Более широкая живая приёмка ещё нужна.
Три судейских слота подключены последовательно и независимо. Каждый получает
свою проверенную методологию через существующий Qdrant/TEI retrieval и публичный
диалог; вердикты предыдущих коллегий не передаются. На один слот вместе с поиском
отведено 60 секунд. Сбой retrieval/модели или неверный вердикт оставляет только этот
слот failed. Проверяются критерий коллегии, точная accepted-цитата, лимит 120 слов,
отсутствие ссылок, методичек, советов, известных закрытых фраз и внутренних ID.
После структурных проверок отдельный вызов reasoned-профиля проверяет наблюдение,
эффект, сравнение и обоснование голоса по публичному диалогу. Только accept
публикует вердикт; reject/uncertain дают invalid_judge_output, недоступность проверки
даёт judge_unavailable. Поиск, генерация и проверка делят прежние 60 секунд на слот.
Проверяющий не получает скрытые вводные, личную подготовку или ответы других коллегий.
Это та же модель, не независимый источник истины: широкая приёмка остаётся задачей.
Добавлен первый модельный Trainer v2: публичный контекст и исходный личный план
пользователя одной строкой, без скрытых вводных, progress и вердиктов коллегий.
Разбор включает эпизоды strengths/mistakes/missed_opportunities, 2–3 задачи next_try,
оценку явно записанной цели и сопоставление плана с разговором. Без подготовки
нет plan_vs_reality и нельзя выдумывать личную цель из фабулы или роли.
Структурные проверки проверяют accepted Evidence, автора действий, дословные
фрагменты подготовки и отсутствие закрытых вводных/ссылок. Отдельный reasoned-вызов
проверяет смысл всех выводов; только accept публикуется. Обе стадии делят 60 секунд.
Неуверенность/невалидный вывод дают invalid_trainer_output, недоступность —
trainer_unavailable; пустой диалог — insufficient_evidence без модели.
Узкая живая приёмка Trainer прошла: 3 HTTP-сценария за 38.35 с суммарно.
Реальный verifier принимает заданный обоснованный разбор и отвергает выдуманное
повышение; реальная генерация + verifier без подготовки возвращают готовый разбор
без выдуманной цели/плана. Остальные модельные роли и retrieval — HTTP doubles.
Диагностика выявила ложную ошибку из-за отсутствия следующего хода после окончания
диалога; генератор уточнён, проверка авторства цитаты сохранена и покрыта регрессией.

Рабочий `/openapi.json` описывает полный формат `V2FinishResponse`: исход, три
судейских слота и тренерский слот.
Перед отправкой ответ валидируется строгой моделью и сериализуется с точными
числовыми значениями. Это реализация формата, не готовность всех компонентов finish.
HTTP-тесты проверяют опубликованную схему, согласованные примеры и соответствие
фактического ответа каноническому JSON Schema; лишние поля и неверные размеры/enum
отклоняются. Живая приёмка тренера и судей остаётся открытой.
Живая приёмка судей не завершена: на Qwen с тестовым retrieval и max_tokens=4096
два слота прошли проверки, negotiation был отклонён; общий прогон занял 157.93 с.
Это не рекомендация менять серверный бюджет и не подтверждение серверного RAG.
Для генерации судей добавлен отдельный профиль `ARENA_QWEN_JUDGE_EXTRA_BODY`:
его верхнеуровневые поля перекрывают `ARENA_QWEN_REASONED_EXTRA_BODY` только в
вызовах судей v2. Без override сохраняется прежний профиль. Для LocalAI в примере
используется `{"metadata":{"enable_thinking":"false"}}`. Это не меняет настройки
модели на сервере и не переключает Guard, Opponent, валидаторы или анализ исхода.
Глобальное отключение рассуждений отклонено после живых регрессий этих стадий.
Подробнее о per-request переключении: [документация LocalAI](https://github.com/mudler/LocalAI/blob/master/docs/content/advanced/model-configuration.md#per-request-override-via-metadata).

## Включение в конфигурации AI-сервиса

При существующей настройке Qwen задайте:

```dotenv
ARENA_MODEL_MODE=qwen
ARENA_V2_ENABLED=true
ARENA_SERVICE_TOKEN=<internal-service-token>
ARENA_V2_TURN_TIMEOUT_SECONDS=60
ARENA_V2_MAX_MODEL_CALLS=8
ARENA_MODEL_MAX_ATTEMPTS=2
```

V2 запрещён без сервисного токена и в demo mode. Пользовательский JWT проверяет
Backend, не AI. Токен не следует помещать в браузер или репозиторий.
Таймаут должен быть конечным положительным числом; лимит вызовов — от 1 до 16.

Backend отправляет `TurnRequest` из rc.1 как JSON, с заголовками
`Authorization: Bearer <internal-service-token>` и
`X-Arena-Contract-Version: 2.0.0-rc.1`. Тело читается из исходных байтов,
числовые Decimal значения не округляются через float. Ответ сериализуется точно.
`/openapi.json` при включённом v2 содержит маршрут, схему тела и ошибки.

| Результат | HTTP | Тело |
| --- | --- | --- |
| Принятый/заблокированный ход | 200 | TurnResponse с candidate snapshot |
| Ошибка модели/исчерпанный бюджет | 200 | model_error, прежний snapshot |
| Нет/неверен сервисный токен | 401 | ServiceError |
| Нет/неверен заголовок версии | 409 | contract_version_mismatch |
| Валидный, но не открытый раунд | 409 | round_closed |
| Некорректный JSON/форма/ссылки/типы/границы | 422 | invalid_request |

ServiceError имеет только `code`, `message`, `retryable`; диагностические тела
провайдера, исходный запрос и закрытые вводные в ошибки не включаются.

## Бюджет и границы

Общий таймаут охватывает управляемый ход после разбора запроса: Guard, Opponent,
TextMatch, проверки политики/новизны и фиксации решения. При timeout локальный
ожидающий запрос отменяется, возвращается `turn_timeout`, snapshot не меняется.
Это не гарантирует, что удалённый сервер немедленно прекратит вычисление.
Лимит вызовов общий для всех ролей, task-local и заново устанавливается на ход.
При исчерпании следующий запрос к модели не отправляется; возвращается код
ошибки текущей стадии. `ARENA_MODEL_MAX_ATTEMPTS` (1–3, по умолчанию 2)
ограничивает число кандидатов Opponent. Guard не повторяется. Если кандидат
не прошёл формат/проверки, он отбрасывается; следующий генерируется из того же
исходного снимка с общим указанием стадии отказа и заново проходит все проверки.
Это не повтор одной оценки до accept, не подстановка условий и не ремонт JSON.
Прежний снимок меняется только после полного успеха одного кандидата; при
исчерпании бюджета или всех попыток остаётся неизменным. Бюджет не перезапускается
между кандидатами и может запретить следующую попытку раньше этого лимита.

Таймер раунда, cutoff, CAS, очереди, дедупликация и сохранение — ответственность
Backend. AI не сравнивает присланный deadline с текущими часами сервера и не
разрешает публикацию кандидата после cutoff: эту проверку делает Backend.
Транспортный обрыв не означает подтверждённый результат; используйте согласованный
command lifecycle. Health endpoints по-прежнему проверяют процесс и общий model
gateway, а не готовность всех ещё не реализованных операций v2.

Добавлен `POST /v2/preparation/review`: выбранный section_id и block_text, контекст
со вводными только пользовательской роли, без opponent brief. Service token и
версия обязательны; неизвестный раздел, неверные роли, лишние поля и пустой блок
отклоняются до модели. Генерация feedback и отдельная смысловая проверка делят 60 с.
Только accept возвращает ready; ошибки/неуверенность дают failed с null feedback.
section_id/revision_id копируются из запроса; сервис не сохраняет и не переписывает
подготовку. Backend сопоставляет revision_id с актуальным блоком перед отображением.
OpenAPI содержит полные request/response схемы; HTTP-тесты сверяют канонический пример.
Это первый срез без живой приёмки качества; вводные оппонента не запрашиваются.

Пока не завершены полный модельный finish и живая приёмка Trainer/review; HTTP info v2,
полный rollout и сквозная приёмка с Backend. Не переключайте весь проект на v2
только на основании наличия одного маршрута.
