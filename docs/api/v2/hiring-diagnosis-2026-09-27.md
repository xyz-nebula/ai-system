# Диагностика hiring в простом evaluate

Статус: причина отказов уточнена, исправление **не завершено**.
Запрос/ответ evaluate, настройки сервера, лимиты и проверки не менялись.

## Воспроизведение через HTTP

После настройки URL/model/профилей LocalAI и SSH-туннеля:

```bash
ARENA_RUN_LIVE_V2=1 uv run pytest -q \
  'tests/test_v2_evaluate_http.py::test_live_evaluate_hiring_returns_a_grounded_verdict[generated]'
```

Тест вызывает публичный `/v2/evaluate`, настоящие генерацию и verifier только hiring.
Остальные модельные стадии недоступны через внешние doubles; retrieval тестовый.
Два исходных сообщения — предложение покупателя и согласие поставщика.
Первый прогон: failed / invalid_judge_output за 10.54 с.
Узкий тест существенно быстрее полного evaluate и не запускает весь AI-контур.

## Что установлено

1. Генератор вернул корректные JSON и индексную цитату, но из инициативы вывел
   «готовность брать ответственность», а согласие назвал пассивностью.
   Verifier вернул reject. Этот отказ не следует обходить.
2. Для контрольного, более буквального кандидата о подтверждении условий
   verifier также вернул reject. Оба контроля вместе: 1 failed / 1 passed, 15.06 с.
   «Буквальный» означает точность описания действий, не доказанную правильность
   выбора коллегии или её критерия: это отдельная часть приёмки.
3. В отдельном диагностическом вызове verifier объяснил отказ отсутствием
   собеседования и данных о качествах сотрудника. Это расходится с вопросом
   профиля hiring в проверенном корпусе: «под чьим управлением я хотел бы работать»,
   а не «кого нанять сотрудником».

Диагностический reason — объяснение модели, не гарантированная трасса её вычислений.
Однако поведение выявляет жанровый фильтр: предмет коммерческих переговоров
используется как причина отказа от самой судейской перспективы.

## Проверенные гипотезы

- Домыслы генератора: подтверждены в захваченном ответе.
- Неверное понимание перспективы hiring: диагностическое объяснение с этим согласуется.
- Отказ корректному по тексту кандидату: воспроизводится, но сам выбор/критерий
  требуют отдельной методической проверки; нельзя автоматически объявлять его верным.
- Одна внутренняя метка `hiring` как единственная причина: не подтверждено.
  В диагностическом вызове удаление метки не устранило отказ (8.80 с).

Уточнение смысла коллегий только в system prompt не прошло контроль:
буквальный кандидат отклонялся, отрицательный — корректно отклонялся.
Первый контроль 16.52 с, усиленное пояснение — 15.05 с.
Экспериментальные инструкции отменены; они не являются проверенным исправлением.
Временная передача reason/изменение model request и debug-логи удалены.

## Следующий срез

Разделить в проверке фактическую точность наблюдения/эффекта/сравнения и логику
ограниченного голоса коллегии. Не требовать совпадения игровых должностей с
гипотетической функцией судьи; при этом не принимать домыслы или голос без связи
с критерием. Сначала определить методически обоснованный положительный контроль
на достаточном диалоге, затем подтвердить positive + negative на живой модели.
Два исходных сообщения могут сами по себе быть недостаточны для убедительного
различия по отдельным критериям: нельзя требовать три ready любой ценой.

Нельзя устранять проблему отключением verifier, превращением reject в accept,
повторами до accept или ветвлением по конкретному кейсу. Полная широкая приёмка
и серверный RAG по-прежнему не подтверждены.

публичные Pydantic-модели запроса/ответа не изменены. Число вызовов и общий
60-секундный лимит коллегии сохранены. Управляемый `/v2/finish` не изменён.

HTTP-тест нового формата сначала был красным: 1 failed / 3 passed;
после реализации — 4 passed. Полный локальный набор: 761 passed / 32 skipped
до добавления четвёртого live-контроля.

отклонён: 2 passed, 14.03 с. Однако генерация с нуля остаётся красной:
1 failed, 13.25 с; verifier вернул reject по всем трём проверкам.

Добавлен более содержательный положительный контроль: поставщик отказывается

Уточнённый контроль прошёл: 1 passed, 7.99 с. Отрицательный контроль повторно
отклонён в предыдущем парном прогоне. Проверки используют тестовую retrieval

### Контроль ложного принятия

Ручной просмотр принятой генерации на четырёх репликах выявил домыслы:
«покупатель ... игнорируя риски», «поставщик выбрал честность» и снижение
вероятности срыва как установленный эффект. Поэтому предыдущие зелёные статусы
не являются доказательством устранения домыслов. Захваченный кандидат добавлен
как `unsupported_bounded`: до исправления 1 failed, 8.88 с (ложное принятие).
Расширение только инструкции facts не помогло: 1 failed / 1 passed, 13.46 с;
эта экспериментальная редакция facts отменена.

Теперь verifier сначала возвращает `unsupported_claims` — дословные фрагменты
из всех трёх полей комментария без подтверждения в репликах, затем три решения.
Непустой список блокирует публикацию независимо от accept. Это всё ещё один
вызов verifier, внутреннее поле не выводится Backend. HTTP red → green:
1 failed / 4 passed → 5 passed. Live ложное принятие устранено на захваченном
кандидате, обоснованный контроль сохранён: 2 passed, 19.72 с.
Временный вывод синтетического текста удалён; авторизация не захватывалась.

С усиленной проверкой генерация на четырёх репликах закономерно стала красной:
1 failed, 18.92 с. Модель повторила захваченные домыслы, теперь они не публикуются.
Компактная инструкция генератора тоже не устранила их: 1 failed / 1 passed,
35.65 с (короткая генерация прошла, расширенная — нет). Компактная инструкция
отменена; сохранены порядок evidence-first и проверка unsupported_claims.
Генератор на расширенном диалоге остаётся незакрытой задачей. Новая защита
устраняет конкретное ложное принятие, но не гарантирует отсутствие других.
Финальный live-прогон сохранённого варианта: новый отрицательный, обоснованный
